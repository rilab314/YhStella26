# 실험 보고서 규약 — PR이 곧 보고서다

**전제.** 사용자는 대화로 경과를 묻는 대신 **GitHub에서 PR을 읽는다.** 그러므로 PR 본문은
리뷰 메모가 아니라 **그 자체로 완결된 보고서**여야 한다. 링크를 따라가야 알 수 있거나,
이전 PR을 읽어야 알 수 있거나, 일지를 펼쳐야 알 수 있으면 실패다.

## 독자 정의 — 이것만 지키면 나머지는 따라온다

> **읽는 사람은 이 프로젝트를 처음 보는 동료다.**
> 딥러닝은 알지만 **이 프로젝트의 지표·조건 이름·내부 약칭은 하나도 모른다.**
> 실험 폴더도, 일지도, 이전 PR도 읽지 않았다.

내가 쓰기 편한 말이 아니라 **그 사람이 읽고 알아듣는 말**로 쓴다. 아래 규칙은 전부
이 한 문장에서 파생된다.

---

## 1. 절대 규칙 6가지

### 규칙 1 — 처음 나오는 모든 이름은 그 자리에서 풀어 쓴다

지표 이름, 조건 이름, 설정 손잡이 이름, 규격 이름, 실행 폴더 이름이 **전부** 해당한다.
설명문은 **`glossary.md`에서 그대로 복사한다** (매번 새로 풀어 쓰면 PR마다 말이 달라진다).
사전에 없는 용어를 쓰게 되면 **먼저 `glossary.md`에 한 줄을 추가하고** 그 문장을 쓴다.

```
✗  `vertex_recall`이 f1을 지배한다
✓  `vertex_recall`(정점 재현율 — 정답 셀 중 디코더에게 실제로 전달되는 점의 비율)이
   최종 성적을 사실상 결정한다
```

### 규칙 2 — 조건(arm) 이름은 설명이 아니다

`alpha075`·`thr015`·`dilate5` 같은 이름은 **폴더를 구분하려고 붙인 꼬리표**일 뿐이다.
결과 표를 내기 **전에**, 조건마다 세 가지를 표로 먼저 밝힌다.

| 밝힐 것 | 예 |
| --- | --- |
| **무엇을 바꿨나** (기본값 → 바꾼 값) | focal loss의 양성 비중 `focal_alpha` **0.25 → 0.75** |
| **평범한 말로 무슨 뜻인가** | 선이 있는 셀을 틀렸을 때의 벌점을 3배로 키운다 |
| **왜 효과가 있을 것이라 봤나** | 놓친 점은 사라진 선이 되므로 거짓 양성보다 비싸다 |

### 규칙 3 — 표에는 열 설명이 붙는다

지표 표를 낼 때는 **바로 위에 그 표를 읽는 법**을 쓴다. 열이 5개를 넘으면 열 설명을
**별도 표**로 뺀다. 각 열에 **↑/↓ (높을수록 좋음 / 낮을수록 좋음)** 을 표기한다.

### 규칙 4 — 숫자는 혼자 쓰지 않는다

절대값만 쓰면 좋은지 나쁜지 알 수 없다. **항상 비교 대상을 함께** 적는다.

```
✗  f1 0.2126
✓  f1 **0.2126** — 대조군 0.1737 대비 **+22.4%**, 천장(완벽한 모델의 상한) 0.976의 22%
```

비교 대상 우선순위: ① 같은 규격의 대조군 → ② 지금까지의 최고 기록 → ③ 천장 →
④ 목표치. 최소 하나는 반드시 붙인다.

### 규칙 5 — 결론을 맨 위에 둔다

첫 두 문단 안에 **"무엇을 했고, 그래서 어떻게 됐고, 무엇을 바꾸는가"** 가 다 나와야 한다.
아래로 내려갈수록 근거가 상세해지는 구조다. 위에서 아래로 읽다가 아무 데서나 멈춰도
그 지점까지 읽은 것만으로 이해가 되어야 한다.

### 규칙 6 — 실패와 한계를 숨기지 않는다

기각된 가설, 틀린 예측, 검증하지 못한 것, 이 결과가 적용되지 않는 범위를 **명시한다.**
특히 내 사전 예측이 틀렸으면 그렇게 적는다 — 그게 다음 실험을 아끼는 유일한 방법이다.

## 2. PR 제목

```
E08 — 검출 재현율을 올리는 4가지 방법 비교 · focal_alpha 0.25→0.75 채택 (f1 +22%)
└실험ID  └무엇을 물었나 (평범한 말)              └무엇을 바꾸나        └효과
```

- 실험 ID는 맨 앞에 붙인다(추적용). **그러나 ID만으로는 아무것도 알 수 없으므로** 반드시
  무엇을 물었는지가 이어져야 한다.
- 내부 약칭을 제목에 쓰지 않는다. `vertex_recall` 대신 "검출 재현율", `U 규격` 대신 생략.
- 효과가 있으면 괄호로 수치를 붙인다. 기각이면 `— 기각` 으로 끝낸다.

## 3. 본문 형식 (실험 PR)

**아래 순서를 지킨다.** 해당 없는 절은 통째로 뺀다 (빈 절을 남기지 않는다).

````markdown
## 요약

<3~5줄. 무엇을 물었고 / 어떻게 나왔고 / 무엇을 바꾸며 / 다음에 무엇을 하는가.
숫자 두세 개를 여기 넣는다. 이 절만 읽어도 보고가 끝나야 한다.>

## 왜 이 실험을 했나

<직전까지 알고 있던 것 → 그래서 생긴 질문. 3~6줄.
이전 실험의 결론을 인용할 때는 링크가 아니라 **한 문장 요약으로 다시 적는다.**>

**가설.** <"~하면 ~가 오를 것이다" 한 문장>
**그렇게 본 근거.** <왜>
**반증 조건.** <이렇게 나오면 가설이 틀린 것. 실험 전에 정했다>
**미리 정한 지목 지표.** <결과를 보기 전에 "이게 움직일 것"이라고 지정한 지표>

## 무엇을 어떻게 바꿨나

<규칙 2. 조건이 여러 개면 표, 하나면 문단.>

| 조건 | 무엇을 바꿨나 | 평범한 말로 | 왜 효과가 있을 것이라 봤나 |
| --- | --- | --- | --- |

## 실험 조건

<규격·데이터량·에폭·GPU·대조군을 **풀어서**. 약칭만 쓰지 않는다.>

| 항목 | 값 |
| --- | --- |
| 규격 | **U 규격(단위 실험)** — 아이디어 비교용 짧은 학습 |
| 데이터 | 학습 3,000장 / 검증 320장 |
| 학습 | 10에폭 · GPU 1장 · 조건당 약 2.5시간 |

**읽는 법.** <이 표에서 무엇을 먼저 봐야 하는지 한 줄>

| 조건 | f1 ↑ | ... |
| --- | --- | --- |

**각 열이 무엇인가**

| 열 | 뜻 |

<번호 매긴 해석 2~4개. 각 항목은 **수치 근거 + 그래서 무슨 뜻인가**.
예측이 빗나갔으면 여기에 적는다.>

## 판정

<채택/무효/기각/보류 + 왜. 판정 기준(±10%)을 여기서 한 번 밝힌다.>
````

## 4. 「다음 실험 계획」 절 — 반드시 넣는다

**보고서는 "무엇을 했나"로 끝나지 않는다.** 이 결과가 다음 행동을 어떻게 바꾸는지까지
써야 읽는 사람이 프로젝트의 방향을 파악한다. 세 부분으로 쓴다.

### (1) 이 결과가 무엇을 바꿨나

```markdown
이 실험 전에는 <무엇을 하려 했었다>. 이 결과가 <어떻게> 바꿨다.
```
바뀐 게 없으면 "우선순위는 그대로다"라고 명시한다 (빈칸으로 두지 않는다).

### (2) 바로 다음 실험 — 한 개만, 구체적으로

| 밝힐 것 |
| --- |
| **무엇을 묻는가** (평범한 말로 한 문장) |
| **어떤 조건들을 비교하는가** (조건마다 무엇을 바꾸는지 — 규칙 2와 같은 수준으로) |
| **미리 정한 지목 지표와 반증 조건** |
| **규격·소요 시간** (예: U 규격, GPU 4장, 약 2.5시간) |
| **언제 시작하는가 / 무엇을 기다리는가** |

### (3) 그 뒤의 대기열 — 표로, 이유와 함께

```markdown
| 순위 | 무엇을 | 왜 지금 이 순위인가 | 규격 |
| --- | --- | --- | --- |
| 1 | ... | ... | U |
```

- **순위의 근거를 반드시 쓴다.** "다음은 백본 교체"가 아니라 "정점 재현율이 병목으로
  확정됐고 백본 계열이 그 값을 바꿀 가능성이 가장 크므로".
- **사람 손이 필요한 항목은 따로 굵게 표시한다** (예: 게이트 승인, 권한). 읽는 사람이
  자기가 할 일을 놓치면 안 된다.
- 대기열의 단일 출처는 `experiment/plan_{mmdd}.md`다. PR에는 **상위 3~5개만** 옮기고,
  옮길 때 약칭을 풀어 쓴다.

## 5. 실험이 아닌 PR

| 종류 | 쓰는 절 |
| --- | --- |
| **도구·버그 수정** | 요약 / 무엇이 문제였나 (**재현 방법과 증상**) / 무엇을 고쳤나 / 검증 / 다음 실험 계획(생략 가능) |
| **문서** | 요약 / 무엇이 사실과 달라졌나 / 무엇을 고쳤나 |
| **설정 기본값 반영** | 요약 / 근거가 된 실험(수치 재인용) / 바뀐 값 표 (기본값→새값) / 영향 범위 / 검증 |

버그 수정은 **증상을 먼저** 쓴다. "이름을 30자로 잘랐다"가 아니라 "실행 ID가 앞부분부터
잘려서 존재하지 않는 폴더 이름이 영구 기록에 남았다 — 30자 이하인 조건은 멀쩡해서
눈에 띄지 않았다".

## 6. 제출 전 자가 검사

**PR을 올리기 전에 본문을 처음부터 다시 읽으며** 아래를 전부 확인한다.
하나라도 걸리면 고치고 다시 읽는다.

- [ ] **약칭 검사** — 본문에 나온 영문 이름·축약어를 하나씩 짚으며 "처음 보는 사람이
      이걸 아나?" 를 묻는다. 모르면 설명이 붙어 있어야 한다.
- [ ] **조건 이름 검사** — `arm` 이름만 있고 무엇을 바꿨는지 없는 표가 있는가?
- [ ] **표 검사** — 열 이름만 있고 뜻이 없는 표가 있는가? ↑/↓ 표기가 있는가?
- [ ] **외로운 숫자 검사** — 비교 대상 없이 혼자 있는 수치가 있는가?
- [ ] **자기참조 검사** — "E05에서 정한 대로", "규칙 4에 따라", "SKILL 11절 절차로" 처럼
      **다른 문서를 읽어야만 이해되는 문장**이 있는가? 있으면 그 내용을 한 문장으로 풀어 쓴다.
- [ ] **첫 문단 검사** — 요약만 읽고 덮어도 무엇을 했고 무엇이 바뀌는지 아는가?
- [ ] **한계 절** — 검증 안 한 것을 적었는가?
- [ ] **다음 계획 절** — 다음 실험이 구체적으로 적혀 있는가?
- [ ] **길이** — 실험 PR은 100~180줄이 적정. 200줄을 넘으면 표를 접거나 근거를 일지로 넘긴다.

**제출 명령**은 파일로 넘긴다 (따옴표 안에 긴 본문을 넣으면 깨진다).

```bash
gh pr create --base main --head <브랜치> --title "<제목>" --body-file <경로>
```

## 7. 실제 사례 — 무엇이 문제였고 어떻게 고치는가

### 고치기 전 (PR #10 원문 — 사용자가 "하나도 이해가 안 된다"고 지적한 부분)

```markdown
**정점 재현율을 올리는 네 손잡이 중 무엇이 f1을 올리는가.** 대조군 `U1_ref`, U 규격
(train 3,000 · val 320 · 10에폭), 마지막 3에폭 평균.

| arm | f1 | coverage | frag | heat_recall | class_fg | vertex_recall | Δf1 | Δvtx |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **alpha075** | **0.2126** | **0.7364** | 7.91 | 0.9545 | 0.4366 | 0.4168 | **+22.4%** | +11.5% |
| thr015 | 0.2053 | 0.7184 | 7.63 | 0.9554 | 0.4368 | 0.4173 | +18.2% | +11.6% |
| U1_ref (대조군) | 0.1737 | 0.6603 | 7.79 | 0.8286 | 0.4511 | 0.3738 | — | — |
```

**무엇이 잘못됐나.** ① "정점 재현율"·"네 손잡이"·"U 규격"·"U1_ref"가 설명 없이 나온다.
② `alpha075`·`thr015`가 **무엇을 바꾼 조건인지 어디에도 없다.** ③ 열 7개 중 뜻이 밝혀진 게
하나도 없고 어느 방향이 좋은지도 모른다. ④ 0.2126이 좋은 값인지 알 수 없다.

### 고친 뒤

````markdown
## 무엇을 어떻게 바꿨나

모델이 **정답 차선이 지나는 셀을 놓치는 것**이 최종 성적의 병목으로 확인됐다(직전 실험).
놓친 셀은 뒤 단계에서 되살릴 방법이 없다. 셀을 더 많이 찾게 만드는 **서로 다른 네 가지
방법을 각각 하나씩만 바꿔** 동시에 돌리고, 어느 것이 실제로 최종 성적을 올리는지 봤다.

| 조건 | 무엇을 바꿨나 (기본값 → 바꾼 값) | 평범한 말로 | 왜 효과가 있을 것이라 봤나 |
| --- | --- | --- | --- |
| **alpha075** | `focal_alpha` 0.25 → **0.75** | 선이 있는 셀을 틀렸을 때의 벌점을 3배로 키운다 | 통상값 0.25는 선이 있는 쪽을 억누른다. 이 과제는 놓친 점이 곧 사라진 선이라 더 비싸다 |
| **thr015** | `heatmap_thresh` 0.3 → **0.15** | 셀을 후보로 뽑는 확률 문턱을 절반으로 낮춘다 | 문턱 근처에 확률이 몰려 있어 조금만 낮춰도 많이 건진다 |
| **topk6000** | 뽑는 방식을 문턱값 → **확률 상위 6,000개** | 매번 정확히 6,000개를 뽑는다 | 문턱 방식은 뽑히는 개수가 에폭마다 요동친다. 개수를 고정한다 |
| **dilate5** | `dilate` 3 → **5** | 고른 셀 주변을 3×3 대신 5×5로 부풀려 함께 후보로 삼는다 | 부풀리기가 재현율의 주 공급원임이 직전 실험에서 확인됐다 |

**각 열이 무엇인가**

| 열 | 뜻 |
| --- | --- |
| **f1** | **최종 성적.** 예측한 선 하나가 정답 선 하나와 짝이 맞아야 정답으로 센다. 짝이 되려면 차선 종류가 같고 정답 길이의 절반 이상을 덮어야 한다 |
| **coverage** | 정답 선 전체 길이 중 예측이 덮은 비율. 즉 놓친 구간이 얼마나 적은가 |
| **검출 재현율** (`heat_recall`) | 선이 실제로 지나가는 셀 중 모델이 찾아낸 비율 |
| **배경 아님 비율** (`class_fg`) | 찾아낸 셀 중 "배경이 아니다"라고 본 비율. 배경이라 불린 셀은 선을 잇는 단계로 전달되지 않는다 |
| **정점 재현율** (`vertex_recall`) | 위 둘의 곱 = 정답 셀 중 **선 잇기 단계로 실제로 전달되는 점의 비율.** 이 실험이 올리려던 값이다 |
| **조각남** (`frag`) | 정답 선 하나를 예측 조각 몇 개가 나눠 덮는가. 1이 이상적이지만 **완벽한 모델도 3.05가 나오므로** 그 값과 비교해 읽는다 |

**참고 눈금.** 완벽한 모델의 상한(정답을 그대로 넣고 잇기만 했을 때)이 f1 **0.976**,
지금까지의 전체 학습 최고 기록이 **0.199**다. 이번 1위 0.2126은 **상한의 22%**이고,
짧은 학습(3,000장·10에폭)으로 전체 학습 최고 기록(8,979장·40에폭)을 넘긴 값이다.
````

## 8. 이 규약을 쓰는 곳

| 언제 | 무엇을 |
| --- | --- |
| **PR을 올릴 때** | 본문 전체를 3절 형식으로 쓴다. `improve-loop` 스킬 11.2절이 여기를 가리킨다 |
| **사용자가 경과·성과를 물을 때** | 같은 원칙(용어 풀어 쓰기·비교 대상·열 설명)으로 답한다. 절 구성은 질문에 맞춘다 |
| **일지(`experiment/`)를 쓸 때** | **적용하지 않는다.** 일지는 나만 읽고 토큰이 비싸다 — 약칭을 그대로 쓴다 |

용어 설명문의 단일 출처는 **`glossary.md`**다. 새 지표·손잡이를 만들면 **그 PR에서
`glossary.md`에 한 줄을 추가한다.** 사전에 없는 말은 PR에 쓰지 않는다.
